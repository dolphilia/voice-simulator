## 1. 決定

手作業で音声ファイルを開き、複数項目を記憶しながらCSVへ入力する方法を廃止する。試聴は、音量確認、練習、各音声の再生、質問、保存、休憩、再開、完了検証までを一つのCLIウィザードで案内する。

回答は原則として「はい／いいえ」の二択にする。A/B比較も、一度にA/B/TIEを選ばせず、次の二択へ分解する。

```text
この観点で差を感じたか
  ├─ はい -> AとBのどちらか
  └─ いいえ -> 同じくらいだと思うか
                 ├─ はい -> SAME
                 └─ いいえ -> UNSURE
```

これにより、「同程度」と「判断できない」を区別する。5段階confidenceは使用しない。

## 2. 目的

ウィザードの目的は次である。

1. 試聴開始前に、再生環境と音量を確認する
2. ファイル操作と手入力CSVを不要にする
3. 音を必要な回数だけ再生し、記憶だけに頼る回答を避ける
4. 一問ずつ短く、平易な言葉で提示する
5. 誤入力、未入力、許容範囲外入力をその場で防ぐ
6. 回答を一問ごとに自動保存し、中断後に再開できるようにする
7. ブラインド性を保ち、条件名や仮説を試聴者へ見せない
8. 知らせない重複提示で回答の安定性を測る
9. 再生回数、中断、回答不能、外乱を記録し、結果解釈へ使う
10. 複数の研究で再利用できる共通方式にする

## 3. 設計原則

### 3.1 一つの画面で一つの判断

同じ音声対について複数の観点を尋ねる場合も、一度に一覧を表示しない。観点ごとに説明、再生操作、質問、回答確認を行う。

### 3.2 再生中もブラインド性を守る

表示してよいもの:

- 進捗
- A/Bという匿名ラベル
- 評価する観点
- 再生・休憩・ヘルプの操作

表示しないもの:

- 条件名
- 刺激ID
- 仮説ID
- 人間音声か合成音か
- 重複提示かどうか
- 正解、集計、過去回答

### 3.3 再生回数を制限しない

テストの意図に反しない限り、A、B、A→Bを何度でも再生できる。再生回数は記録するが、評価中に良し悪しを表示しない。

8回以上再生した場合は、回答を急がせず「判断が難しい可能性があります。休憩するか、判断できないを選べます」と案内する。再生を禁止しない。

### 3.4 記憶による比較を避ける

質問の直前と質問中に再生操作を利用できるようにする。別の提示へ移った後に過去回答を見返して修正する機能は設けない。ただし、次の提示へ進む前の確認画面では直前回答だけを訂正できる。

### 3.5 疲労を結果から分離する

- 5提示ごと、または10分ごとに休憩を提案する
- 任意の時点で安全に中断できる
- 再開時は再生機器と音量が同じか確認する
- 長時間の中断後は短い音量確認をやり直す
- 試聴開始、終了、休憩時間を記録する

### 3.6 互換CSVは出力物にする

回答の正本は構造化JSONとイベントログにする。`responses.csv`はウィザードが自動生成する互換出力とし、ユーザーへ直接編集させない。

## 4. ウィザード全体の流れ

```text
起動
  -> セッションとhashの検証
  -> 再生プログラムの検出
  -> 静かな環境・機器の確認
  -> 音量校正
  -> 操作練習
  -> 本番説明
  -> 提示1
       -> A/B再生
       -> 主質問
       -> 必要な補助質問
       -> artifact確認
       -> 外乱確認
       -> 回答確認・自動保存
  -> ...
  -> 定期休憩
  -> 隠し重複提示
  -> 完了検証
  -> 回答JSON/CSV生成
  -> ブラインドを保った完了表示
```

仮説別結果、重複一致率、選択条件名は、試聴終了後の別コマンドでだけ表示する。

## 5. 起動前検証

ウィザードは音を再生する前に次を確認する。

- session manifest、lock、全音声が存在する
- 音声hashがlockと一致する
- 回答schema versionを解釈できる
- presentation IDが重複していない
- 非公開keyの内容がblinded manifestへ混入していない
- 指定されたaudio playerを実行できる
- 端末が対話入力を受けられる
- 既存progressがある場合、同じsession lockを参照している

失敗時は本番を開始せず、修正方法を日本語で示す。

## 6. 音声再生

### 6.1 player adapter

標準では次の順に利用可能なplayerを検出する。

1. macOS `afplay`
2. `ffplay -nodisp -autoexit`
3. `mpv --no-video`
4. Linux `aplay`

実行時はshell文字列を組み立てず、引数配列でsubprocessを起動する。音声パスを画面へ表示しない。

`--player`で明示指定できるようにする。CIとテストでは、実音声を再生しないfake playerを注入する。

### 6.2 再生操作

本番中の基本操作は次とする。

| 入力 | 動作 |
| --- | --- |
| `a` | Aを再生 |
| `b` | Bを再生 |
| `p` | A、短い間隔、Bの順に再生 |
| `r` | 直前に再生したものを再生 |
| `y` | はい |
| `n` | いいえ |
| `1` | Aを選ぶ |
| `2` | Bを選ぶ |
| `h` または `?` | ヘルプ |
| `q` | 保存して中断 |

回答と再生の入力が衝突しないよう、現在有効な入力だけを毎回表示する。大文字・小文字、前後空白は正規化する。

### 6.3 再生順

最初の比較再生はA→Bとする。左右条件はセッション生成時に均衡化するため、全体ではrecency biasを抑える。個別再生は自由に行える。

同じ提示内で再生順を自動的に変えない。どちらを聞いているかの取り違えを避けるためである。

## 7. 音量校正

### 7.1 安全原則

- システム音量をプログラムから変更しない
- 「最大音量」へ上げるよう案内しない
- 最初は小さめの音量から始めるよう案内する
- 快適に聞こえない場合は本番を開始しない
- 校正は聴力検査ではないことを明記する

### 7.2 校正音

セッションと同じsample rate、安定部に近いRMSで、次の完全生成校正音を用意する。

- 緩い包絡を持つ倍音音
- 帯域制限ノイズを薄く含む音

実験候補そのものは校正に使わない。校正音のpeakとRMSを自動gateし、session manifestへhashを保存する。

### 7.3 校正手順

```text
静かな環境ですか?                         y/n
同じ機器を最後まで使えますか?             y/n
音量を低めにしましたか?                   y/n

[校正音を再生]
音は明瞭に聞こえましたか?                 y/n
大きすぎず、快適ですか?                   y/n

両方yes -> 練習へ
noあり   -> 調整案内後、校正音を再生し直す
```

環境に関するnoは無理にyesへ誘導しない。「後で再開」を選べるようにする。

### 7.4 再開時

再開時は次を確認する。

- 前回と同じ再生機器か
- システム音量を変えていないか
- 前回から長時間経過したか

異なる機器または音量の場合、校正をやり直し、機器変更イベントを保存する。

## 8. 練習

本番刺激を使わない練習対を一つ用意する。

練習では次を確認する。

- A/Bを個別再生できる
- ペア再生できる
- yes/noの回答方法が分かる
- 「同じくらい」と「判断できない」の違いが分かる
- 保存して中断できることを理解する

既知の分かりやすい差を持つ完全生成音を使い、誤答した場合は正解を教えるのではなく、操作方法と質問の意味を再説明してもう一度練習する。練習回答は本番結果へ含めない。

## 9. 質問形式

### 9.1 比較質問

各観点を次の二択列で聞く。

```text
Q1. この観点で、AとBに差を感じましたか?     y/n

yes:
  Q2. より当てはまるのはどちらですか?        A/B

no:
  Q2. 同じくらいだと思いますか?              y/n
      yes -> SAME
      no  -> UNSURE
```

`SAME`は「ほぼ同程度と判断した」、`UNSURE`は「比較を成立させられなかった」として分析上分ける。

### 9.2 artifact質問

四択を一度に提示せず、左右を別々に聞く。

```text
Aに、クリック・継ぎ目・不自然なノイズなどの加工違和感がありましたか? y/n
Bに、クリック・継ぎ目・不自然なノイズなどの加工違和感がありましたか? y/n
```

結果としてneither/A/B/bothを得られるが、ユーザー操作は常に二択である。

### 9.3 外乱質問

各提示の最後に聞く。

```text
再生中に外の音、音切れ、操作ミスなど、判断を妨げることがありましたか? y/n
```

yesの場合は理由タグを選び、その提示をprimary analysisから除外して後半へ一度だけ再配置する。元回答と再提示の両方を保存する。

### 9.4 自由記述

自由記述を必須にしない。まず任意の理由タグを数字で選べるようにする。

- 息っぽい
- 掠れ
- 機械的
- 楽器的
- ループ感
- クリック・継ぎ目
- 母音が違う
- 音量差が気になる
- その他

`その他`を選んだ場合だけ短い自由記述を受け付ける。何も選ばず進められる。

## 10. 質問ルーティング

すべての提示で「人間らしさ、開始、持続」の三軸を機械的に聞かない。仮説ごとに、試聴前にprimaryとsecondaryを定める。

| 比較 | primary | secondary | artifact |
| --- | --- | --- | --- |
| H1 onset対stable | 人間の発声に近い | 開始が自然 | 両側 |
| H3 gain対複合開始 | 人間の発声に近い | 開始が自然 | 両側 |
| H4 人間ループ変動 | 持続が自然 | 人間の発声に近い | 両側 |
| H4 合成相関構造 | 人間の発声に近い | 持続が自然 | 両側 |
| H5 formant ablation | 開始が自然 | 目的母音に聞こえるかを左右別yes/no | 両側 |
| H6 長短ループ | 持続が自然 | 人間の発声に近い | 両側 |
| control 原音対短縮 | 加工違和感 | 人間の発声に近い | 両側 |

質問ルーティングはblinded manifestへ匿名のquestion template IDとして保存する。ウィザードは仮説IDを読まない。

## 11. 重複と精度確認

### 11.1 固定重複

13ユニーク比較に対して4比較を重複する。次を満たすようセッション生成時に選ぶ。

- onset、sustain、syntheticの主要群を含む
- 元提示との間を最低4提示空ける
- 連続配置しない
- 重複時はA/Bを独立に再ランダム化する
- 試聴者へ重複を知らせない

重複回答は独立票として効果量を増やすために使わず、評価者内一貫性の確認に使う。

### 11.2 適応的再提示

外乱があった提示だけを、最大一回、後半へ再配置する。`UNSURE`や`SAME`を理由に自動再提示しない。判断不能を誤答扱いして圧力をかけないためである。

### 11.3 一貫性

一貫性は左右ラベルではなく、実際に選択されたconditionへ戻して判定する。

- A/B選択の一致
- SAME / UNSUREの再現
- artifact左右判定の一致
- 再生回数の極端な差

一致率が低い場合、仮説を機械的に棄却せず、評価困難または効果が閾値付近として報告する。

### 12.1 blinded-session.json

ウィザードが読む唯一の提示定義とする。

- session ID、schema version
- presentation IDと順序
- A/Bの匿名音声ファイル
- question template ID
- 校正音と練習音
- 休憩規則
- hash

condition、hypothesis、duplicate_ofを含めない。

### 12.2 private-session-key.json

分析器だけが読む。

- presentationとconditionの対応
- hypothesis
- duplicate_of

試聴完了前に開かない。

### 12.3 progress.json

- 完了した質問
- 現在位置
- 校正状態
- 使用機器の自己申告

一問ごとに一時ファイルへ書き、flush後にatomic renameする。

### 12.4 events.jsonl

追記専用で次を記録する。

- 起動、終了、中断、再開
- 校正再生と確認
- A/B/pairの再生
- 質問提示、回答、直前訂正
- 休憩
- player error
- 外乱申告

音量の実値や個人情報は収集しない。

## 13. 既存チェックポイントの移行

現在の `results/listening/checkpoint/` は未回答であり、候補音声と13ユニーク比較はそのまま有効である。一方、手入力CSV、5段階confidence、全軸一括回答、隣接した重複提示を含むため、新方式の本番には使わない。

移行手順:

1. 既存ディレクトリとlockを変更・削除しない
2. 同じ13ユニーク比較と同じ音声hashを読み込む
3. `checkpoint-wizard-v1/`へ新しいblinded sessionを生成する
4. 4重複、最低間隔、A/B再ランダム化を新seedで固定する
5. question routingを事前固定する
6. 旧セッションを `superseded-unanswered` とする移行記録を、新セッション側へ保存する
7. 旧セッションに回答がないことをhash付きで記録する
8. 新セッションを試聴前にlockする

これは候補や仮説の差し替えではなく、未回答段階での提示・入力方式の改訂として扱う。


## 16. エラーと中断

### player error

- その提示を未回答のまま保つ
- error内容とplayer名をイベントへ保存する
- 別playerを検出・選択できるようにする
- 再生できるまで回答画面へ進まない

### Ctrl-C / 端末終了

- シグナルを捕捉できる場合は保存して終了する
- 捕捉できない場合も直前の質問までatomic save済みとする
- 再開時に未確定質問からやり直す

### 誤入力

- 許可された入力を再表示する
- 無効値を保存しない
- 3回連続で誤入力した場合は短いヘルプを表示する

### session変更

- lockまたは音声hashが変わっていればprogressを継続しない
- 古いprogressを上書きせず、理由を表示する

## 17. 分析

### 17.1 primary response

- `A`または`B`: 条件選択
- `SAME`: 同程度という判断
- `UNSURE`: 比較不能。方向集計の分母から除き、比率を別報告

### 17.2 artifact

左右yes/noをconditionへ戻し、各条件のartifact選択率を出す。

### 17.3 完遂品質

- 完了提示数
- 外乱率
- UNSURE率
- 1提示あたり再生回数
- セッション時間と休憩
- 固定重複の一致率
- player error

再生回数が多い回答を自動的に無効化しない。効果が小さい、質問が難しい、疲労がある等の診断に使う。

### 17.4 重み付け

- 重複は独立票として数えない
- 最初の有効回答をprimaryとする
- 重複は一貫性として併記する
- 外乱による再提示では、再提示側をprimaryとし元回答を監査用に残す
- 結果を見て規則を変更しない
