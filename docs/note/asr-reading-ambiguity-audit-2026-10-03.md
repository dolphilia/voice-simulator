# ASRかな変換の読み曖昧性：保存済み結果の追加監査

2026-10-03。[内容評価](acoustic-revision-content-evaluation-result-2026-10-02.md)の封印を保持し、200件の保存済み認識文を静的に調べた。**音声生成・再認識・学習・ダウンロードは0回**。追加実験の承認を得たとは解釈せず、既存音声への採否を変更していない。

## 実装と観測

既存pyopenjtalkの共有ライブラリが公開しているMeCab C APIで、既存OpenJTalk辞書のN-best形態素解析を取得した。新しい辞書を導入していない。C APIとN-best解析の使用方法は[MeCab公式資料](https://taku910.github.io/mecab/libmecab.html)に対応する。使用したライブラリと辞書全ファイルの実ハッシュは[契約](../../research/experiments/acoustic-revision-content-evaluation/post-evaluation/reading-audit-20261003-v2/contract.json)に保存した。

原稿の正解を与えずに、上位16解析経路を得る。最上位解析と同じ形態素境界・品詞・活用・原形を持つ経路だけを残し、同一表記の読み候補を記録する。人名への品詞変更や別の単語分割を混ぜない。[実装](../../research/experiments/acoustic-revision-content-evaluation/reading_audit.py)は音声を読まず、元のCERも計算し直さない。

「金の響く」では、一般名詞の「金」について「キン」「カネ」を含む複数の候補が得られた。主たるかな変換がキンを選んだことと、カネという辞書候補が存在することを、原稿へ合わせた語の置換なしに確認できた。

保存済み200認識は57種類の異なる文字列だった。辞書読み候補が複数ある箇所を含むのはWhisperで41/100件、Reazonで53/100件、異なる文字列では23件。数字等の読みが形態素辞書の段階では未確定の箇所はWhisper10件だった。[個別結果](../../research/experiments/acoustic-revision-content-evaluation/post-evaluation/reading-audit-20261003-v2/summary.json)を保存した。

これらは誤りの件数ではない。たとえば正しく認識された「鐘が響く」「雨が降り始めました」にも辞書候補の複数性がある。Reazonで曖昧性の印が多いことを、認識が劣るという意味に使わない。

## 採否へ使える範囲

この処理は、読み変換に敏感な比較を確認する補助診断である。上位16経路に全ての読みが含まれる保証はなく、連濁など文脈に合わない候補もあり得る。辞書の読み候補を、話された発音の正解とは呼ばない。

さらに、この出力はOpenJTalkの助詞・数詞などの後処理前である。数字「2」はこの段階で読み未確定になった。字句の候補を連結して完全な音素列とみなし、候補の最小CERを採否に使う方法は採らない。これだけで内容評価や知覚評価の資格が得られたとも認定しない。

今後の契約では、**従来の固定かなCERを保持し、辞書曖昧性を別欄として残す**。辞書候補がないことを音声の正しさの証拠にしない。読み変換の疑義がある差は、音声改善／悪化の確証として解釈しない。実際の発音との差を決めるには、独立した音素・かなの認識証拠または適格な境界／発音資料が別途必要となる。

## 検査・保存・残る作業

原稿なしの複数読み取得、品詞制限、カタカナ対照、空入力、NUL拒否、数字の未確定、終了済みハンドルの拒否を検査した。元の223封印ファイルと辞書の全ハッシュは実行後も一致した。辞書データの条件は同梱の`DICTIONARY-COPYING`に保持した。

最初の実装は、C APIのオプション文字列で引用した辞書パスを渡した際に初期化が失敗した。音声・認識処理へは進んでいない。[失敗記録](../../research/experiments/acoustic-revision-content-evaluation/post-evaluation/reading-audit-20261003-v1/failure.json)とその時点のソースを保持し、公開APIへ引数配列で渡す方法へ修正した。

元の目標は未達である。共同補正の切り分けは[追加実験案](../plans/acoustic-control-factorial-proposal-2026-10-02.md)の承認待ちで、自然さの資格・局所イベント・未使用集合での最終確認も残る。今回の静的監査で生成・評価の上限を増やしてはいない。
